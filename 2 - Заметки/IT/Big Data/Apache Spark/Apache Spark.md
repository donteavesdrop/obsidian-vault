❖ Накладные расходы обусловлены сериализацией данных, 
дисковым вводом-выводом и репликацией файловой системы 
HDFS.
❖ Большинство приложений Hadoop тратят более 90% времени на 
выполнение операций чтения-записи HDFS.

Spark будет хранить промежуточные 
результаты в распределенной памяти вместо 
стабильного хранилища (диска), обеспечив 
прирост в быстродействии вычислений.

![[Pasted image 20260408122431.png]]

Каждый запрос будет подразумевать дисковый ввод-вывод при 
обращении к файловой системе HDFS, что может составить 
большую часть времени выполнения приложения.

![[Pasted image 20260408122451.png]]

Если к одному и тому же подмножеству данных 
выполняются неоднократно различные запросы, эти 
данные могут сохраняться в распределенной памяти 
для ускорения доступа

![[Pasted image 20260408122505.png]]


❖ Приложения Spark выполняются как независимые наборы процессов в 
кластере, координируемые объектом SparkContext в основной 
программе (называемой программой драйвера).
❖ Для работы в кластере SparkContext может подключаться к нескольким 
типам диспетчеров кластеров, которые распределяют ресурсы между 
приложениями.

1. После подключения Spark получает исполнителей на узлах в 
кластере, которые представляют собой процессы, выполняющие 
вычисления и хранящие данные вашего приложения. 
2. Spark отправляет код вашего приложения (определенный файлами 
JAR или Python, переданными в SparkContext) исполнителям.
3. SparkContext отправляет задачи исполнителям для выполнения

Режимы работы Spark
❖ Local
❖ В локальном режиме один исполнитель работает в той же 
JVM, что и драйвер. Этот режим полезен для тестирования 
или выполнения небольших работ.
❖ Standalone
❖ Вы можете запустить автономный кластер вручную, 
запустив мастер и рабочие процессы.
❖ YARN
❖ Ваше spark-приложение может быть запущенно на Hadoop-
кластере, под управлением менеджера YARN.
❖ Kubernetes
❖ Spark может работать в кластерах, управляемых 
Kubernetes. Эта функция использует собственный 
планировщик Kubernetes, специально добавленный в Spark.

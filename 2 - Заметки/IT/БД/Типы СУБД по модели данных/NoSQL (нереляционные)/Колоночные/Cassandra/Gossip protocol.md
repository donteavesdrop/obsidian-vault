Что такое Cassandra?
![[Pasted image 20260408120339.png]]
Cassandra — это база данных NoSQL, предназначенная для обработки больших объемов данных на множестве обычных серверов, обеспечивающая высокую доступность без ущерба для производительности. Cassandra изначально была разработана в Facebook Авинашем Лакшманом и Прашантом Маликом для поддержки функции поиска в почтовом ящике. Он был вдохновлен DynamoDB от Amazon и Bigtable от Google. Позже он был выпущен как проект с открытым исходным кодом под эгидой Apache Foundation. Хотя Cassandra доступна как проект с открытым исходным кодом, коммерческую поддержку предлагают такие компании, как DataStax, которая предоставляет дополнительные функции и поддержку для развертывания Cassandra.


Проблемы управления в распределённых системах
Распределённые системы часто сталкиваются с серьёзными вызовами. Узлы системы могут выходить из строя, восстанавливаться, менять своё состояние. Для управления этим процессом необходимо решать задачи согласования данных, отслеживания конфигурации и обмена информацией между узлами. Например, для корректного распределения запросов нужно знать текущее состояние узлов и назначать их для обработки на основе заданных правил.

И протокол обмена сплетнями как раз предоставляет децентрализованный способ навести порядок в больших кластерах


Почему именно Gossip Protocol![[Pasted image 20260408120420.png]]
Gossip — это одноранговый протокол связи, в котором узлы периодически обмениваются информацией о состоянии о себе и о других узлах, о которых они знают. Процесс сплетен в Cassandra запускается каждую секунду и обменивается сообщениями о состоянии с другими узлами в кластере. Каждый узел независимо всегда выбирает от одного до трех узлов для сплетен. Он всегда выбирает активного пира (если таковой имеется) в кластере, он вероятностно выбирает начальный узел из кластера или, возможно, вероятностно выбирает недоступный узел. Узлы обмениваются информацией о себе и о других узлах, о которых они сплетничали, поэтому все узлы быстро узнают обо всех других узлах в кластере.

![[Pasted image 20260408120435.png]]

Вся система в конечном итоге получит конкретное сообщение с высокой вероятностью. Говоря простым языком, протокол сплетен — это технология, с помощью которой узлы строят глобальную карту посредством ограниченных локальных взаимодействий

Стратегии распространения сообщения через протокол сплетен
![[Pasted image 20260408120829.png]]
Протокол сплетен является оптимальной основой для создания высокодоступного сервиса. Стратегия распространения сообщения через протокол сплетен должна выбираться на основе требований сервиса и доступных сетевых условий. Существуют компромиссы с точки зрения пропускной способности, задержки и надежности для каждой стратегии распространения сообщения.

Push-модель эффективна, когда имеется лишь несколько сообщений об обновлении из-за накладных расходов на трафик. Узел с последним сообщением отправляет сообщение случайному подмножеству других узлов в push-модели

В pull Модели Каждый узел будет активно опрашивать случайное подмножество узлов на предмет любых сообщений об обновлении в модели pull. Этот подход эффективен, когда есть много сообщений об обновлении, поскольку он с большой вероятностью найдет узел с последним сообщением об обновлении 

Модель push-pull оптимальна для быстрого и надежного распространения сообщений об обновлениях. Узел может push-уведомить о новом сообщении об обновлениях, а также может опрашивать о новых сообщениях об обновлениях. Подход push эффективен на начальном этапе, когда имеется лишь очень мало узлов с сообщениями об обновлениях. Подход pull эффективен на заключительном этапе, когда имеется множество узлов с большим количеством сообщений об обновлениях

Производительность протокола Gossip
Число узлов, которые получат сообщение от конкретного узла, называется fanout . Количество раундов сплетен, необходимое для распространения сообщения по всему кластеру, называется cycle

Например, для распространения сообщения по 25 000 узлов требуется около 15 раундов сплетен. Интервал сплетен может быть установлен на значение всего лишь 10 мс для распространения сообщения по большому центру обработки данных примерно за 3 секунды. Распространение сообщения в протоколе сплетен должно автоматически устаревать, чтобы уменьшить ненужную нагрузку

Циклы, необходимые для распространения сообщения по кластеру = O(log n) до базы разветвления, где n = общее количество узлов

Метрики производительности
производительность реализации протокола сплетен можно измерить с помощью следующих метрик:

•остаток: количество оставшихся узлов, не получивших сообщения, должно быть минимальным

•трафик: среднее количество сообщений, отправленных между узлами, должно быть минимальным

•конвергенция: каждый узел должен получить сообщение как можно быстрее

•среднее время: среднее время, необходимое для отправки сообщения на каждый узел, должно быть небольшим

•время последнего: время, необходимое последнему узлу для получения сообщения, должно быть небольшим

Обмен сообщениями по принципу «сплетни» очень похож на трёхстороннее рукопожатие TCP. При использовании обычного протокола широковещательной рассылки за один раунд может быть отправлено только одно сообщение, и данные могут постепенно распространяться по кластеру. Основные компоненты протокола

Gossiper:

•Gossiper — это центральный компонент, отвечающий за управление обменом сплетнями между узлами в распределённой системе. Он управляет состоянием каждого узла и следит за актуальностью информации о других узлах. Он использует информацию, полученную через сообщения GossipDigest, для принятия решений о том, как распространять информацию по сети. Также он отвечает за обновление состояния каждого узла на основе полученных данных.

EndpointState:

•EndpointState представляет собой данные о состоянии конкретного узла в сети, такие как версия состояния, информация о репликации и другие метаданные. Это состояние используется для решения, нужно ли обновить информацию о другом узле. Если узел A узнаёт, что информация о узле B более актуальна, чем его собственная информация о B, то он обновляет своё состояние на основе данных из EndpointState, полученных в сообщении.

GossipDigest:

•GossipDigest — это сжато представленная информация о состоянии другого узла. Она включает в себя адрес узла и максимальную версию его состояния, что помогает другим узлам быстро определить, есть ли у них более актуальная информация, чем та, что представлена в сообщении. Это позволяет сократить объём передаваемых данных, делая обмен более эффективным.

Реализация протокола Gossip
Gossip работает по принципу случайного выбора узлов для передачи сообщений, используя протоколы UDP или TCP для передачи данных. Одним из важных аспектов является использование службы выборки одноранговых узлов, которая помогает идентифицировать другие узлы для обмена сообщениями.

Служба выборки использует рандомизированный алгоритм для выбора одноранговых узлов, что помогает избежать излишней нагрузки на систему. API этой службы предоставляет две ключевые конечные точки: /gossip/init, которая возвращает список узлов, известных конкретному узлу при запуске, и /gossip/get-peer, которая возвращает адрес независимого однорангового узла.

Рабочий процесс сервисов одноранговой выборки
При запуске каждый узел инициализируется частичным представлением всей системы. Это представление включает небольшой список других узлов, с которыми узел может обмениваться сообщениями. Этот процесс помогает уменьшить нагрузку и обеспечивает обновление состояния системы.

Протокол использует механизм объединения точек зрения узлов на бирже сплетен, что позволяет каждому узлу обновлять свою локальную таблицу членства. Важно отметить, что для выбора одноранговых узлов используется вероятностное распределение, что помогает избежать передачи дублирующих сообщений одному и тому же узлу.

API протокола Gossip для обмена состоянием
![[Pasted image 20260408121039.png]]
Протокол Gossip также используется для обмена состоянием приложения между узлами. Для этого предоставляются несколько конечных точек API. Например, /gossip/on-join используется для сообщения о присоединении нового узла к сети, а /gossip/alive и /gossip/dead — для мониторинга состояния живых и мёртвых узлов. Эти сообщения помогают поддерживать актуальность данных в системе.

Кроме того, имеется конечная точка /gossip/change, которая используется для обновлений состояния, где отправляются изменения данных в виде пар ключ-значение.

Роль начальных узлов
Начальные узлы являются критически важными для работы системы, поскольку они предоставляют полную информацию о сети на старте. Протокол сплетен использует начальные узлы для предотвращения возможных логических разделений в сети и обеспечения согласованности данных.

Эти узлы играют роль отправной точки для всех новых узлов, которые присоединяются к системе, и позволяют избежать изоляции данных.

Обновление данных через сообщения Gossip
![[Pasted image 20260408121112.png]]
Обновление данных через сообщения Gossip происходит следующим образом: каждый узел сравнивает входящие сообщения с данными, которые он уже содержит, и обновляет свою локальную базу данных, добавляя отсутствующие значения. Этот процесс обмена данными гарантирует, что узлы синхронизируются и получают актуальную информацию.

Если узел получает данные, которых у него нет, он добавляет их в свою локальную базу, а также отправляет обратно недостающие данные в ответном сообщении для других узлов.

Версионирование и Таймер сплетника
В системе Gossip используется версионирование данных с помощью номеров версий, что позволяет отслеживать изменения состояния узлов. Это гарантирует, что более новые данные всегда заменяют старые. Таймер сплетника гарантирует, что все узлы получат актуальные данные, даже если они находятся за разделом сети.

Каждый узел поддерживает свой собственный heartbeat, который включает в себя генерацию и номер версии, чтобы обеспечить корректность и актуальность информации.

HeartBeatState
![[Pasted image 20260408121139.png]]
Приведённые далее реализации очень близки, но не идентичны исходному коду Cassandra. Cassandra реализует собственные сериализаторы почти для всех нижеперечисленных

HeartBeatState используется для управления состоянием узлов в распределённых системах.

Состоит из номера генерации и номера версии. Номер генерации остаётся неизменным во время работы сервера и увеличивается при каждом запуске узла. Используется для различения информации о состоянии до и после перезапуска узла. Номер версии совпадает с номерами состояний приложения и гарантирует упорядоченность. С каждым узлом связано одно состояние HeartBeat.

•Generation нужен для идентификации изменений, вызванных перезапуском узла, чтобы отличать старые состояния от новых.

•Version синхронизирует изменения между узлами, чтобы все изменения происходили в правильном порядке.

Код HeartBeatState:

•Класс HeartBeatState инкапсулирует состояние узла.

•Метод updateHeartBeat() увеличивает версию через класс VersionGenerator.

•Методы forceNewerGenerationUnsafe() и forceHighestPossibleVersionUnsafe() используются для принудительных изменений generation и version в особых случаях.

•Новый узел создаёт объект HeartBeatState с generation = 1 и version = 0.

•При обновлении версии используется метод updateHeartBeat(), чтобы гарантировать согласованность изменений в распределённой системе.

ApplicationState

![[Pasted image 20260408121205.png]]
В отличие от HeartBeatState, которое отвечает за общий статус узла, ApplicationState предоставляет информацию о более специфических аспектах работы узла, например, о текущей нагрузке, токенах, версиях данных и так далее.

ApplicationState

Состоит из состояния и номера версии и представляет состояние одного «компонента» или «элемента» в Cassandra. Например, состояние приложения для «информации о загрузке» может быть (5.2, 45), что означает, что загрузка узла равна 5.2 при версии 45. Аналогично, узел, который выполняет самозагрузку, будет иметь состояние приложения «самозагрузкой»: (bxLpassF3XD8Kyks, 56), где первое — токен самозагрузки, а второе — версия. Номер версии совместно используется состояниями приложения и HeartBeatState для гарантии упорядоченности и может только расти.

EndPointState

![[Pasted image 20260408121224.png]]
EndPointState

Включает все ApplicationStates и HeartBeatState для определенных узлов. EndPointState может включать только один из каждого типа ApplicationState, поэтому если EndPointState уже включает, скажем, информацию о нагрузке, новая информация о нагрузке перезапишет старую. Номер версии ApplicationState гарантирует, что старое значение не перезапишет новое.

EndPointStateMap
![[Pasted image 20260408121241.png]]
endPointStateMap

Внутренняя структура Gossiper, которая содержит информацию о состоянии конечных точек для всех узлов (включая себя), о которых она узнала.

Пример работы:

1.Узел запускает Gossiper.

2.EndPointStateMap создаётся и заполняется:

1.Узел добавляет информацию о себе.

2.Получает информацию о других узлах (через gossip).

3.При обновлении:

1.Узел получает данные об изменении состояния другого узла.

2.EndPointStateMap проверяет версии и обновляет только те записи, которые устарели.

Можно подумать, что у нас может быть базовый класс Message с GossipDigestSynMessage GossipDigestAckMessage и GossipDigestAck2Message в качестве дочерних классов. Однако такая иерархия наследования приведёт к жёсткой привязке, и любое изменение будет иметь каскадный эффект для всех связанных классов. Чтобы решить эту проблему, лучше дуиспользовать композицию.

Объект «Сообщение» будет иметь общую полезную нагрузку (которая может быть любой из GossipDigestSyn, GossipDigestAck и т. д. или любым другим объектом, который мы хотим передать ~ возможность комбинирования).

«сплетни» — это своего рода форма программирования на основе событий, то есть действия должны выполняться в ответ на определённые события. Это можно распространить не только на «сплетни», но и на другие функции Cassandra. Для этого в Cassandra есть «глаголы» и соответствующие им «обработчики». При получении сообщения узел анализирует связанный с ним глагол и запускает соответствующий обработчик, передавая весь объект сообщения в качестве аргумента. Затем обработчики извлекают полезную нагрузку и продолжают выполнение.

Класс InetAddressAndPort

·Класс InetAddressAndPort представляет собой структуру, которая комбинирует IP-адрес узла и его порт, предоставляя уникальную идентификацию узла в сети. Это важная часть внутренней структуры системы, поскольку каждый узел должен быть однозначно идентифицирован для правильной маршрутизации сообщений и поддержания связи в распределённых системах.

Типы сообщений

Теперь давайте сосредоточимся на том, какая информация содержится в каждом из упомянутых трёх сообщений и как узлы в кластере используют обработчики для обновления и обмена информацией, чтобы все работало.  
Cуществует несколько разных типов сообщений

GossipDigestSyn

•Это сообщение используется для передачи информации о текущем состоянии системы (например, о версиях и состояниях данных).

•Оно используется для синхронизации состояния между узлами.

При получении сообщения GossipDigestSyn, одноранговый узел выполняет следующие действия:

1.Получение адреса узла отправителя для ответа ACK.

2.Извлечение gossipDigestList из сообщения.

3.Формирование ответа ACK, который включает:

1.DeltaEpStateMap (карта конечных точек) для узлов, о которых отправитель не знает или имеет устаревшую информацию.

2.Список дайджестов для узлов, которые имеют более низкую версию.

4.Отправка ответа ACK с актуальной информацией.

Каждое сообщение связано с глаголом, который сопоставляется с обработчиком 
GossipDigestSynVerbHandler.

GossipDigestAck

•Этот тип сообщения является ответом на GossipDigestSyn. Узел, получивший запрос, подтверждает получение данных, подтверждая состояние, которое он хранит.

•В этом сообщении могут передаваться метаданные о состоянии узла.
GossipDigestAckMessage — это подтверждение, отправляемое в ответ на получение сообщения GossipDigestSynMessage. Это второй этап трёхстороннего обмена сообщениями в протоколе Gossip, который позволяет узлам синхронизировать свои данные.

При получении сообщения GossipDigestAck, узел-инициатор выполняет следующие действия:

1.Получение адреса узла отправителя для отправки ответа Ack2.

2.Извлечение списка gossipDigestList и карты EndpointStateMap из полезной нагрузки.

3.Формирование ответа Ack2, который включает:

1.deltaEpStateMap (карта конечных точек) для узлов, о которых узел-инициатор не знает или для которых у него есть более новая информация.

4.Отправка ответа Ack2.

Каждое сообщение обрабатывается соответствующим глагольным обработчиком GossipDigestAckVerbHandler.

GossipDigestAck2

•Это продолжение предыдущего типа сообщения. Оно используется для более детальной синхронизации, когда требуется дополнительная информация о состоянии данных или узла.

•Этот тип сообщения может включать больше данных о состоявшихся изменениях.  
Остановимся на их реализации подробнее
GossipDigestAck2Message — это подтверждение, отправляемое в ответ на получение сообщения GossipDigestAckMessage. Это третий и последний этап трёхстороннего обмена сообщениями в протоколе Gossip. После этого обмена оба узла (X и Y) синхронизируют свои данные о состоянии известных им узлов.

При получении сообщения GossipDigestAck2, одноранговый узел выполняет следующие действия:

1.Извлечение карты EndpointStateMap из полезной нагрузки.

2.Обновление локального состояния с помощью информации из полученной карты.

Обработчик GossipDigestAck2VerbHandler просто обновляет локальное состояние с использованием полученной карты EndpointStateMap.

На GossipDigestAck2Message завершается процесс синхронизации между узлами

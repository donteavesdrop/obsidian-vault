## Индексирование

### Когда используются индексы

- **Быстрый поиск** записей по условию `WHERE`
- **Объединение таблиц** с помощью `JOIN` (необходимо использовать одинаковые типы сравниваемых полей; если требуется преобразование типов, индексы использоваться не будут)
- **Выборка наименьшего количества записей** из таблицы (при множественном индексе используется тот, который находит меньшее число строк)
- **Поиск `MAX` и `MIN`** для ключевых полей
- **Сортировка и группировка** таблиц (`ORDER BY` и `GROUP BY`)
- **Извлечение данных из индексного файла** (возможно только в некоторых случаях, например, когда все извлекаемые поля проиндексированы)

---

## Принципиальная схема индекса

> Записи в индексах **упорядочены**, а записи в таблице — **нет**.  
> При создании индекса значения атрибутов могут комбинироваться и преобразовываться.

## Как используется индекс при поиске строк

1. **Планировщик** СУБД проверяет, имеется ли для таблицы индекс, созданный на основе тех же столбцов, что указаны в условии `WHERE`
2. Если индекс существует, планировщик **оценивает целесообразность** его использования
3. Если использование целесообразно:
   - Сначала выполняется **поиск необходимых значений в индексе**
   - Затем, если значения найдены, производится **обращение к таблице** по указателям из индекса

> Таким образом, полный перебор строк в таблице заменяется поиском в упорядоченном индексе и переходом к строке по прямой ссылке.

## Создание индекса

```sql
CREATE INDEX имя_индекса ON имя_таблицы (имя_столбца, ...);
```

### Пример

Создадим индекс для таблицы `airports` по столбцу `airport_name`:

```sql
CREATE INDEX ON airports (airport_name);
CREATE INDEX

\d airports
...
Индексы:
...
"airports_airport_name_idx" btree (airport_name)
...
```

> 📌 **Важно:** индексы автоматически создаются для ограничений `PRIMARY KEY` и `UNIQUE` (для быстрой проверки дублирования).

---

## Составные индексы

Индекс может быть создан **по нескольким столбцам**:

```sql
\d boarding_passes

Индексы:
"boarding_passes_pkey" PRIMARY KEY, btree (ticket_no, flight_id)
"boarding_passes_flight_id_boarding_no_key" UNIQUE CONSTRAINT, btree (flight_id, boarding_no)
"boarding_passes_flight_id_seat_no_key" UNIQUE CONSTRAINT, btree (flight_id, seat_no)
```

| Элемент | Значение |
|---------|----------|
| `btree` | тип индекса (В-дерево, по умолчанию) |
| имена столбцов | поля, по которым создан индекс |
| суффикс `_key` | вид ограничения, для которого создан индекс |

## Эксперимент: выборка без индекса

```sql
\timing on   -- включаем секундомер в psql

SELECT count(*) FROM tickets
WHERE passenger_name = 'IVAN IVANOV';

-- Время: 373,232 мс
-- count: 200
```

> ⚠️ Эти значения времени нужно рассматривать лишь как качественные ориентиры.

---

## Эксперимент: индекс создан

```sql
CREATE INDEX passenger_name ON tickets (passenger_name);
-- Время: 4023,408 мс (однократные затраты на создание)

SELECT count(*) FROM tickets
WHERE passenger_name = 'IVAN IVANOV';

-- Время: 17,660 мс  ← стало на порядок меньше!
```

---

## Удаление индекса

```sql
DROP INDEX passenger_name;
DROP INDEX
```

## Ряд замечаний

- Когда индекс уже создан, о его **поддержании в актуальном состоянии** заботится СУБД
- Это требует от СУБД **затрат ресурсов и времени**
- Индекс по столбцу, участвующему в `JOIN`, может ускорить выборку
- При сортировке (`ORDER BY`) индекс также может помочь, если сортировка выполняется по тем же столбцам

---

## Селективность индекса

- Если в запросе есть `ORDER BY`, индекс может позволить **избежать этапа сортировки**
- Если запрос просматривает **значительную часть таблицы**, явная сортировка может оказаться быстрее использования индекса

### Правило

> Индексы более полезны, когда из таблицы выбирается **лишь небольшая доля строк** (высокая селективность выборки).

| Термин | Значение |
|--------|----------|
| **Высокая селективность** | выбирается малая доля строк → индекс эффективен |
| **Низкая селективность** | выбирается большая доля строк → индекс может не дать эффекта |

## Важные замечания

### ⚠️ Влияние на производительность

> **Увеличение числа индексов замедляет операции добавления, обновления и удаления строк таблицы**, поскольку при этом приходится обновлять сами индексы.

### 💾 Затраты памяти

Индексы занимают **дополнительный объем памяти**. Перед созданием индекса следует убедиться, что планируемый выигрыш в производительности запросов превысит дополнительную затрату ресурсов компьютера на сопровождение индекса.

## Индексирование. Итоги

| Тип индекса | Когда использовать |
|-------------|--------------------|
| **btree** | В большинстве случаев — стандартный выбор |
| **GIN / GiST** | Для специфических случаев (полнотекстовый поиск, геоданные и т.д.) |
| **Битовые и hash-индексы** | Активно используются в процессе выполнения запросов |

### 🔑 Ключевые выводы

- ✅ **Частичные индексы** могут заметно сократить объем индексов
- ✅ В PostgreSQL нужно **явно создавать индексы для FOREIGN KEY**
- ✅ Можно получить **очень большой выигрыш** при использовании **покрывающих индексов**
- ⚠️ Каждый индекс требует **дополнительных затрат** на своё поддержание
